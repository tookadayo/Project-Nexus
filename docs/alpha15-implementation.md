## Implemented scope

Web onboarding now checks the signed-in user's current Discord membership and native/delegated authority on the API side, without requiring a Discord link command. The short-lived API proof binds the real session, user, tenant, method, path and mutation origin. New installations are confirmed before setup; existing configuration is reviewed in four sections and applied through a versioned draft. Blank optional values remain optional. An explicit scope expansion needs confirmation. Discord setup controls lead to Web setup, retaining the existing stop/delete safety controls. Installation notices use a persistent delivery ledger and only an already configured administration destination or an explicitly permitted system destination; without one, status is Web-only.

The dashboard includes current run allowance, unavailable/unknown results, existing flows, upcoming occurrences and links to the editor. Japanese and English are supported. Authenticated event receipts distinguish pending admission, started runs and skipped events; an accepted click is not presented as a successfully completed run. Unsupported triggers and operations remain labelled with their limitations.

The editor uses a single typed tree for stacked blocks and the accessible Steps alternative. It supports shape plus colour distinctions, typed fixed values/variables/calculations, nested bounded control flow, unused blocks, undo, explicit target scope, date/time-zone input, schedule previews and simulation inputs. Saving, validation, simulation, impact review and enabling are bound to one immutable revision and semantic hash. Simulation uses the production pure evaluator with clearly marked mock clocks/draws/outcomes, consumes no production run or approval, and cannot send to Discord. Missing inputs cannot become a successful test receipt.

Execution state, committed random choices, approvals and operation outcomes are durable. A wait and an entire run are bounded by seven days. Every external operation has a durable claim before dispatch; interrupted or ambiguous writes become UNKNOWN and cannot be replayed automatically. Adopted connectors include ordinary posts, validated Legacy text/embeds, editing a post whose successful send is proven in the same run, approved ordinary role additions/removals, public threads and category-scoped text-channel creation. Ticket reads return only current state and version under the original feature's access, scope and logical retention cutoff. A category's verified current overwrites and age restriction are copied explicitly, then checked again before dispatch. No arbitrary route, code or HTTP action is exposed. Discord has no conditional transaction spanning its read and write APIs, so a concurrent external administrator change after the final check remains a platform limitation.

Parallel branches run through durable cooperative contexts, with isolated branch variables, explicit named outputs, all-branch joins and shared deadlines/budgets. A branch waiting for time or formal approval does not prevent another eligible branch from advancing. Restart, cancellation and UNKNOWN states preserve confirmed outcomes and cannot repeat an interrupted external write. Safe API projections show branch states and due times without exposing saved values.

Internal triggers are restricted to committed, existing structured intake requests; ordinary analytical/attention events do not qualify. Interaction starts pass through the existing verified Discord HTTP/Gateway and acknowledged encrypted-job boundary, then an actor-bound, single-use, fifteen-minute native component instance. The currently verified clicker is the run actor. Capture is bounded, metadata is cleared after admission/skip, status receipts are erased within seven days, and recovery cannot replay old events. See [trusted event contracts](alpha15-trusted-events.md).

Every ordinary role change requires a formal receipt binding the exact inputs, run/revision and live permission-policy digest. The requester and approver are independently reauthorized; native authority, hierarchy, protected roles, allowed capabilities and channel access changes are checked. A process-local Gateway channel census plus current complete REST metadata proves coverage; missing or obfuscated coverage stops role changes. Five role starts per rolling minute per guild is an additional technical burst guard. [Role safety and topology limits](alpha15-role-safety.md) explain why separate processes currently fail closed.

The Scheduler and trusted event pump poll independently every 250ms, each with one in-flight pass; slow Discord effects do not block it. More than one second of lateness is recorded as skipped rather than replayed as backlog. Generations, fixed occurrence keys and reservation transactions prevent stale/duplicate starts. A manual run uses the actual requester's current identity; scheduled/internal runs use the enabling actor and revalidate that person. Global stop rejects new manual runs before quota reservation and skips/advances scheduled occurrences without catch-up. Privacy, Beta and automation locks use a consistent order. Member/guild erasure reaches new state; offline tombstone application disables restored definitions/schedules, expires approvals, fences pending event receipts and component instances, and stops restored runs. Migrations through 059 are required before restoring tombstones, including per-Run event-wait fences and schedule-review invalidation.

Global stop also fences existing work atomically in the settings transaction. A stop/resume entirely between worker passes cancels old queued runs, expires old approvals, clears/skips pending event admission and invalidates native component instances. Internal intake committed while stopped creates no automation receipt. Both transitions advance a schedule cutoff, so even an old occurrence inside the one-second lateness tolerance is skipped after resume. Fresh inputs may use the retained active definition. A second cancellation/deadline check under the quota row lock prevents an unstarted reservation from becoming consumed during a concurrent stop; started usage and confirmed/UNKNOWN external-operation evidence remain intact.

Direct cancellation treats both STARTED and UNKNOWN operations as unresolved. If an ambiguous operation result is committed just before cancellation, the cancellation flag cannot terminalize the run as CANCELLED before the runtime records UNKNOWN. The regression interrupts that exact checkpoint gap, invokes the actual cancellation service, and verifies retained consumed usage and no resend on a later tick.

## Small local measurement and technical limits

The probe in `.local/alpha15-measurement.json` ran 100 pure arithmetic/serialization samples on Windows, Node 24.18.1, Ryzen 7 9800X3D, 16 logical CPUs and 33,436,094,464 bytes of RAM. It took 3.832ms in total: p50 0.0169ms, p95 0.0722ms, maximum 1.0221ms. Maximum synthetic record size was 222 bytes; heap delta 267,360 bytes, RSS delta 2,129,920 bytes. CPU accounting reported zero at the OS timer's resolution. There were zero external requests. This is a small baseline probe, not a production throughput or Discord latency measurement.

Initial invitation Beta guardrails are three active flows per guild, a combined allowance of 100 reserved/consumed runs per UTC calendar month, one active run per guild and host, 20 pending runs per guild and 100 per host. A run is consumed once when actual processing starts; cancellation before that releases its reservation. Stored definitions are capped at 20 flows per guild, 20 revisions per flow, 8MiB per guild and 64MiB per host, including retained revisions awaiting deletion. These are conservative technical admission guards, not paid-plan entitlements, prices or a measured production capacity claim. Grammar is shared across existing plans; existing analysis/attention entitlements and pricing are not repurposed.

Run state, inputs/draws, operation evidence and diagnostic events are purged within the approved seven-day window after termination by worker maintenance. Definitions remain while active and are purged within seven days after deletion. Diagnostic events contain status/IDs/codes, not bodies, tokens or variable values. Monthly aggregate quota counters contain no run IDs, identities or payload and survive execution-record deletion so erasure cannot refill the allowance; a closed month is removed after its seven-day reconciliation grace. Existing analytical history and administrative audit policies remain separate.

## Remaining work and release gates

Required external acceptance inputs are collected in [external validation](alpha15-external-validation.md). These gates are distinct from implemented local paths and from the separate condition/arithmetic redesign.

- New-form and message-metadata triggers, general event sources/readers beyond the adopted ticket wait/recheck subset, event-relative schedules and additional Discord families remain unavailable. V2, Modal, attachments, buttons/select components in user-authored message values and arbitrary external APIs are not adopted by the automation transport. The original-approved A19 common gaps, including typed results, ranges, mapping/list operations, definition management and elapsed schedules, are addressed in the current section below. Candidate catalog presence alone is not completion.
- Current conditions use true/false/unknown branches. An if nested in the false branch implements an ordered else-if chain, with the first matching branch alone and a final optional else. There is no dedicated multi-elif UI. A future UI could flatten that existing tree for editing; explicit elif and the broader Scratch condition/arithmetic redesign await the parent's separate design and were not added here.
- Rules-based AI remains reserved for alpha16; it was not added to this release.
- Role changes are available only when the current complete Gateway/REST coverage contract and native permission checks succeed. Separate Gateway/API/worker processes do not share this ephemeral proof and cannot approve or execute role mutations. No Administrator permission or persistent census store was added as a workaround.
- Existing invitations record operational eligibility, not independently verified age, contractual capacity or a versioned acceptance of terms. No new personal attestation or retention purpose was invented. The operator's legal eligibility process still needs a separate decision.
- Fresh-install guidance prefers the existing administration notification channel; otherwise the approved default uses the current system channel only with a proven fresh installation and current View/Send checks immediately before dispatch. Unknown capabilities or no safe destination remain Web-only with an explicit next action. Ambiguous delivery is never resent to another destination. There is no guaranteed message when Discord supplies no permitted destination.
- Actual Discord/OAuth, public HTTPS, screen-reader hardware, onamae.com deployment and hosted load/backup recovery were not exercised. Windows runtime, Node/PostgreSQL/Redis architecture and loopback operator separation are retained. Deployment compatibility is not a hosted acceptance result.
- Seven-day backup expiration, current protected deletion-journal preservation and an offline restore drill must be confirmed in the target deployment. No host security or backup settings were changed.
