# alpha.10 structure, scope and observation stabilization

Preimplementation review: 2026-10-08 (Asia/Tokyo). Start HEAD `71a27f937e8dd534c40c767033d91a492cdce44c`, master `5638fe34a9169c95b6fb138222bcd4a84d8ee97d`, existing draft PR #4. The root implementation record owns refreshed GitHub verification.

Reuse CommunityModel channel/tag mappings, saved measurement recipes, discovery snapshots, current surface state, lifecycle inbox deduplication, typed reaction/poll state, member eligibility, collection epochs and metric evidence. Keep all/include/exclude legacy settings meaningful. Category additions in new setup expand reviewed children into saved IDs; future children require another explicit selection. Paginated batch editing accompanies bounded schema growth, so arrays never silently truncate.

Change unconditional parent resolution in analytics, lifecycle, attention and journey queries. Introduce a small shared typed resolver: actual channel ID remains the location of activity; only public/announcement threads inherit parent channel settings. Categories provide explicit grouping/default purpose and cannot contain activity. Private threads, unknown channel kinds, deleted/forbidden locations and missing thread parents cannot collect. Explicit exclusion overrides category inclusion; explicit channel purpose survives moves. Bot visibility says nothing about public disclosure permission.

Add location post metadata separately from eligible participant activity. Staff announcements and Bot/Webhook posts are counted as observed posts without adding Bots to participant counts. Human subject hashes support existing privacy deletion. No text, images, names or poll answer meaning are stored. Direct replies and first human Forum response are distinct definitions; awaiting response applies only to administrator mapped support/bug-report locations. Showcase, announcement, onboarding, unconfigured and casual locations cannot create response obligations. Archive/lock is not resolution; only mapped stable tag IDs or explicit operations can resolve.

Conflict: existing attention treats unmapped first newcomer posts as reply obligations; it must require confirmed purpose. Existing post analysis uses participant eligibility and silently omits announcements. Legacy persisted results retain their old versions; changed calculations receive definition v2 and final root analysis recipe v3, preventing comparison with v1 and the earlier v2 population-completeness claims.

Migration 046 is immutable. New 047 adds tombstones/collection prohibition and a separate minimal location-post projection. No history, monthly balance or reservation is reset. Existing all scopes continue to follow available channels; only a new explicit setup confirmation creates a fixed include scope. Old metadata cannot reconstruct excluded historical Bot posts and must remain marked as incomplete rather than invented.

Migration 050 separately marks historical participant-only provenance, including imported `observation-v3` rows, and records per-Guild location collector introduction even when there are no posts. Old and crossing windows produce positive lower bounds, conditional reply/waiting evidence and unknown unsupported zero; they cannot compare. Valid direct-reply semantics remain separate from incomplete population coverage. The introduction marker participates in scoped input identity, survives member deletion and is removed by server deletion. Stop old Gateway/Worker processes before migration, then start the new runtime: prior epochs are closed and pre-introduction event replay cannot reopen them. Collection gaps at the window start are incomplete even when PostgreSQL microsecond boundaries round to a JavaScript millisecond.

No changes to plan allowances, billing policies, automatic role/channel updates, private-thread collection, LLM classification, Presence, audio capture, individual rankings, native server guide, or live Discord servers.

Current dependencies: discord.js 14.27 / discord-api-types 0.38.55 API v10. Channel types 0/2/4/5/10/11/12/13/15/16 and typed permissions match existing SDK constants. Forum starter message IDs equal thread IDs; ordinary Forum messages need no reply reference to provide an observable human response. Threads inherit parent visibility; private thread access remains excluded. Poll result absence differs from a confirmed zero and multi-answer counts are not unique voters. External event signup is distinct from observed attendance and needs no event channel. Future obfuscation metadata is handled explicitly using the SDK channel flag rather than names.

Acceptance uses fictitious server structures, failing-first unit/integration tests and generated payload tests. Live Discord acceptance and Hosted acceptance remain NOT RUN unless separately executed with authorization.

Additional official review: [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits), checked 2026-10-08. Existing DiscordRest parses Retry-After / body retry_after, per-resource bucket and global scope; bounded retries respect the provider delay. Capability refresh scheduling adds deterministic jitter. Reused unchanged. Do not hardcode a throughput guarantee or treat Interaction acknowledgement latency as aggregate execution throughput.

Implementation notes: `analysisChannelScope` reconciles current structure and deletion/permission states with discovery metadata. The shared resolver is used by detailed analytics, chart exploration, Web overview/canonical analytics, adaptive/journey presentation, attention and Helper delivery. Explicitly selected public threads remain semantic anchors; automatically inherited thread creation does not change selected parent anchors. New `ANNOUNCEMENTS` and `SHOWCASE` analyses select their confirmed purposes independently. Showcase starter count excludes Forum/Media comments; comments do not require Reply references. Voice co-presence counts unique member episodes, avoiding repeated connections displayed as people. Current reaction/poll state last observed in the period is not a historical vote-total reconstruction; poll participants are distinct subject hashes, not answer-count sums. Stored legacy reply definitions remain preserved by migration.

Tag status: stable parent/tag ID mappings may explicitly mark RESOLVED or UNRESOLVED. Conflicting applied status tags produce a settings review caveat and cannot resolve a post. Request-purpose tags and resolution tags are different roles; a request that has been resolved is valid. Tag names, archive and lock never decide status.

The S1–S8 database matrix seeds the documented actual structure, selected human post occurrences, distinct announcement/showcase/support results, and the exact purpose-qualified Attention set. S8 additionally exercises category movement, a newly discovered unselected sibling, and permission loss overriding an older visible snapshot. Existing adaptive tests verify voice/AFK/Stage/event/tag observation behavior; owner/billing transitions belong to the commercial suite. The matrix does not claim to execute every change listed in the fixture contract. A typed discord.js cache observation can establish a previously missing ordinary location before discovery; it cannot infer a type from a message, collect private threads, or resurrect a tombstone.

Limitations: Discord cannot prove guide reads, satisfaction, content quality, conversations, external attendance or message semantics. Historical Bot/Webhook posts discarded by earlier ingestion cannot be restored. Thread parent metadata absent from both discovery and current state fails closed rather than expanding the server scope. Deletion tombstones survive stale structure replay and archived-state retention; live permission verification at external delivery boundaries remains the existing dispatcher responsibility. No live Discord or Hosted acceptance is represented by local payload or SQL checks.
