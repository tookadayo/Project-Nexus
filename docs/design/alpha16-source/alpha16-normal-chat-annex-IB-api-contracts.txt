B-1-7. Idempotency-Key

状態変更APIのIdempotency-Key scopeは、

authenticatedActor
+ guildId
+ operationContractId
+ targetId

を基本scopeとする。

さらに同一Keyのrequest fingerprintとして、

HTTP method
+ normalized path
+ canonical query
+ body canonical hash
+ If-Match
+ expected/targetVersion

を固定する。

body canonical hashは、JSON objectのkey順序・whitespace等による表現差を除いて同じ意味のrequestが同じhashになるよう、alpha16でcanonicalization ruleを固定する。

同時要求

同じscope＋Key＋fingerprintが同時到着した場合：

先行要求：通常処理

後続要求：409 IDEMPOTENCY_IN_PROGRESS

後続要求は副作用を起こさない

処理完了後の同一Key要求：

保存済みresponseをそのまま返す

domain処理を再実行しない

同Keyでbody等が異なる：

409 IDEMPOTENCY_KEY_REUSE

新しい処理を開始しない

期限切れKey：

409 IDEMPOTENCY_KEY_EXPIRED

古いKeyを新規操作として再利用しない

Idempotency recordを理由としてRunの保存期間を延長しない。

期限値は別途承認対象であり、本付録では採用済み保持期間を設定しない。

B-1-8. If-Match / version

共有resourceを変更するAPIでは原則としてIf-Matchを要求する。

例：

If-Match: "12"

headerなし → 428 PRECONDITION_REQUIRED

現在versionが12 → 処理可能

現在versionが13 → 412 VERSION_MISMATCH

If-Matchはresourceそのもののversionを保護する。

一方、Suggestionが参照する対象resourceについてはbodyのtargetVersionを使用する。

Suggestion version ≠ target version

であることに注意する。

Suggestion version不一致 → 412 VERSION_MISMATCH

target version不一致 → 412 TARGET_VERSION_MISMATCH

versionは一致するが現在stateが「実行不可」→ 409 STATE_CONFLICT

B-1-9. Cursor pagination

List APIはcursor paginationを基本とする。

提案初期仕様：

sort = createdAt DESC, resourceId DESC

同一timestampをIDでtie-breakする。

cursorはopaque signed tokenとし、少なくとも以下を結び付ける。

guild scope

endpoint

filter

sort

snapshot boundary

last sort position

cursor version

expiration metadata

cursorを改変した場合は400 INVALID_CURSOR。

別guild、別filter、別sortでcursorを再利用してはならない。

snapshot

最初のページ取得時にlogical snapshot boundaryを確定する。

後から作成された新規recordを途中ページへ割り込ませない。

削除/tombstoneされたrecordはprivacy/domain policyを優先して表示対象から除外する。削除されたrecordを復活表示するために履歴データを再公開してはならない。

更新によってsort keyが変化する場合はcursor境界と矛盾しないように扱い、同一cursor走査中に重複・逆順が生じる設計を避ける。

完全なDB歴史snapshotを長期間保持することは要求しない。

同期read

初期提案：

許容調整範囲：5～30秒

同期DB mutation

初期提案：

初期提案：

5～10秒

長時間処理そのものをHTTP request中に待たない

これらはCloudflare等の外部サービス制限値ではなく、NEXUS application timeoutの未検証提案値である。

timeoutしたmutationについて、

「responseを受け取れなかった」
≠
「処理されなかった」

とする。

したがって、

status照会

Idempotency状態照会

read-only reconcile

を優先し、未知の副作用をblind retryしない。

特にRESULT_UNKNOWNの外部副作用を自動再送しないことは確定契約である。

    "requestedAt": "2026-10-15T08:35:00.000Z",
    "completedAt": "2026-10-15T08:36:00.000Z",
    "restoreProtection": "tombstone_reapplied"

restore処理が存在する場合も、

backup restore
→ tombstone再適用
→ 削除対象を再びアクセス可能にしない

を必須とする。

B-13. 保持期間とAPI設計上の制約

既存方針として以下を固定する。

Run終了後の最小状態：7日以内に削除

backup：7日

30日保持：採用しない

24か月保持：採用しない

Run情報をevidence/history/idempotency等へ複製してRun保持を延長しない

Fact、Suggestion、履歴、監査、Idempotency等は論理的に別分類となり得るが、保持期間は本付録では承認値にしない。

未承認候補として過去に挙げた、

Idempotency：24時間候補

Suggestion/履歴：30日候補

集計系：24か月候補

はいずれも未採用である。

別分類を設けても、Run終了後7日以内削除という制約を回避する目的でRun payloadを複製してはならない。

B-15. 実routeとの照合条件

各提案APIを実装対象へ変換する前に、既存codeについて以下を照合する。

同一機能の既存routeが存在するか

methodが一致するか

request body/schemaが一致するか

response schemaが一致するか

session取得方法が一致するか

guild scopeをserver側で確認しているか

permissionをserver側で確認しているか

mutationにdomain invariantが通っているか

version/optimistic concurrencyが存在するか

既存のerror codeがあるか

既存UIが想定するempty/loading/error状態

DB transaction境界

外部副作用の有無

idempotencyの既存実装

PC APIとの既存署名契約

既存routeがあることだけを理由に、本付録の安全境界を弱めてはならない。

逆に、既存routeが本付録と異なることだけを理由にrouteを全面新設することもしない。
