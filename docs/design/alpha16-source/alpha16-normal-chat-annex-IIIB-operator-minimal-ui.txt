付録III-B：Operator最小運営UI契約

位置付け：設計契約のみ。実装・設定変更・テスト・動作確認は行わない。
Operatorは独立Fastifyをloopback限定で稼働させ、Tunnel/public BFFへ公開しない。以下のroute・permission名はすべて提案名であり、現コードとの照合は未実施。現コードで確認済みなのはprivacy retention/tombstone基盤であり、Operator画面/API/permissionの実装存在・全対象mappingは未照合である。

0. III-Aからの整合修正

同一deletion intentのreplay
Idempotency-Key/receiptに紐付く同一intentは、再認証済み状態だけを理由に拒否せず、現在のsession権限・対象scope・tombstoneを再検査したうえで、受付番号・現在state等の限定statusだけを返す。過去のpreview/confirm response本文は再返却しない。新しいintentは既存tombstoneがあれば拒否する。

GLOBAL/GUILD削除の直列化
同一人物を対象とするGLOBAL/GUILD intentは共通target guardで直列化する。GLOBALがGUILDを包含する場合は既存job参照を統合して扱い、GUILD操作からGLOBALへ自動昇格しない。

Operator APIエラー分類
400 INVALID_REQUEST / 401 AUTH_REQUIRED / 403 PERMISSION_DENIED / 404 TARGET_NOT_FOUND / 409 STATE_CONFLICT / 409 TOMBSTONED / 412 VERSION_MISMATCH / 428 PRECONDITION_REQUIRED / 410 PREVIEW_EXPIRED / 422 SCOPE_MISMATCH / 429 RATE_LIMITED / 503 DEPENDENCY_UNAVAILABLE をstable codeとして提案する。副作用結果不明は通常のretryable errorにせず、既存Runtime契約のUNKNOWNとして返す。
Previewの範囲変化はtarget identity・scope・plan revision・権限の変更を指し、新規row到着そのものでは無効化しない。tombstone後に到着する対象rowも削除・再生成・再取得を遮断する。

1. 共通Operator command

mutation requestの共通必須構造は以下とする。

field	契約
target	targetType:string、targetId:string、scopeKind:string、`scopeId	null`。Discord IDはopaque identifierとして保持し、型変換しない
idempotencyKey	mutation必須。client-generated opaque string。同一command/target/scopeに限定
ifMatch	revisionを持つ対象では必須。serverの現在revisionとCAS比較。*は禁止
previewHash	危険操作で必須。server生成previewのcanonical SHA-256 hash
stepUpToken	危険操作で必須。server発行。client生成値は受理しない
reason	停止・状態変更・公開・取下げ等で必須。自由な個人情報を記録しない

共通responseはrequestId、operationId|null、state、revision、updatedAt、errorCode|nullを基本とし、秘密値・token・個人本文を返さない。

3. 画面共通状態

全画面でloading / empty / active / stale / conflict / unavailable / unknownを区別する。
UNKNOWN・STALE・UNAVAILABLEを成功状態として表示しない。一覧更新中も直前値を「現在値」と誤認させず、lastObservedAtを併記する。

操作ボタンはサーバーが返す許可操作だけを表示する。ただしボタンの存在自体は認可ではなく、全mutationでserver-side permission・scope・revisionを再検査する。

4. Operator境界

Operatorは127.0.0.1等のloopback interfaceだけにbindし、0.0.0.0等の公開interfaceにはbindしない。

Tunnel/public BFFからOperator routeへproxyしない。

Operator自身もloopback到達だけを認証根拠にせず、III-Aのsession、CSRF、Origin、Host、再認証を利用する。

Hostは許可されたloopback hostだけを受理し、任意のForwarded/X-Forwarded-*を信用しない。信頼proxyを置く場合も明示設定されたproxyだけを信頼する。

Browser→OperatorはOperator自身のsame-originだけを使用し、DB/Redis/PC内部APIへBrowserから直接接続しない。

Discord Gateway/RESTはPCからの直接outboundであり、Tunnel経由ではない。Operatorの「Tunnel到達性」とDiscord outbound状態を同一状態にしない。

5. 削除・復元・監査の最小表示規則

Privacy画面では対象Discord ID、scope、含むデータ、残るデータ、不可逆境界、receipt、現在stateだけを表示する。Discord上の他者メッセージ削除とは表示・操作とも明確に分離する。

削除後は通常sessionで対象データを閲覧させない。session失効後はIII-Aの限定receiptによるstatus確認だけを許可し、通常認証・復活・他データ閲覧には使用できない。

Auditには対象を特定するための最小targetだけを残し、名前、メール、投稿本文、secret、token、削除対象データのコピーを保存しない。

6. 実装段階の境界

alpha16：この付録で定義した画面構造、route契約、permission gate、state/revision、publication/deletion/runtimeとの接続契約を対象とする。既存機能を全面rewriteせず、既存正本へ差分接続する。

全体動作確認はalpha16の実装が全部完了してから一括実施する。現段階では受入条件を定義しただけであり、A配置の承認も実装承認・本番稼働承認ではない。
