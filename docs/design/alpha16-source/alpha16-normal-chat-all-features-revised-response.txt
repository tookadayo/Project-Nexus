1. alpha16の基本方針

NEXUS alpha16では、Web・分析・Automation・AIを別々のシステムとして扱わず、次の一つのRuntime体系として設計する。

ユーザー向けUIはWeb、永続状態・認証処理・分析・ルールエンジン・Automation・Scheduler・外部サービス連携はWindows NEXUS Server PCを中心に実行する。

ただし、公式サイトなどの静的コンテンツだけはレンタルサーバーへ配置できる。

したがって、

「WebをサーバーPCへ置く」ことと「NEXUSの実行処理をサーバーPCへ置く」ことを分離する。

72. Next.jsについての追加注意

alpha16ではNext.jsをPCへ配置する場合、現在のコードが依存しているrequest-time機能を維持することになる。

Next.js公式ではNode.js server deploymentはフル機能をサポートする一方、static exportは制限付きで、CookiesやHeadersなどrequest-time機能を利用できない。

したがってA案では、

Next.jsを静的exportしない。

通常のNode.js serverとしてPC上で稼働させる設計を基本とする。

また、現在のNext.js versionは今回確認していない。公式では2026年10月14日にセキュリティ更新が案内されているため、実装開始前には実際のversionとpatch状態を別途確認する。これは現在のNEXUSコードが既に対応済みという意味ではない。

Discordの2026年のDeveloper Policy/Privileged Intents変更を考慮し、Message Content等の取得は必要最小限とする。Discord自身もMessage Content、Guild Members、PresenceをPrivileged Intentsとして区別している。

75. 最終判断
推奨

alpha16ではA案を推奨する。

ただし、A案を単純な「Next.jsをPCへコピー」として扱わない。

正確には、

Static Public Web + PC-hosted Next.js/BFF + PC Domain API + PC Runtime

という構成にする。

これが現在の、

Browser → same-origin Next.js BFF → signed PC API

という実際のコード構造との互換性が最も高い。

B案について

B案は不適切なのではない。

むしろ将来的には、

Static Dashboard + direct PC API

は非常に綺麗な構成になる。

ただし現在のコードには、

Explore DB access

Operations DB access

Billing server logic

が存在するため、alpha16でBへ直接移行すると変更範囲が大きくなる。

したがって、

alpha16 = A

将来 = Bへ移行可能

という二段階構成が最も合理的。

76. alpha16の最重要設計原則

最後に、今回の改訂でNEXUS全体を貫く原則を固定する。

① レンタルサーバーはStatic Public Surface

公式Web、Legal、公開Announcement、公開Status等。

② Windows PCはNEXUS Runtime

Auth、DB、Analysis、Explore、Operations、Automation、Scheduler、Billing、Rule Engine、Suggestion、Discord連携等。

③ TunnelはNetwork Boundary

Tunnel自身を認証・guild認可・Runtime正本として扱わない。

④ Browserは内部API秘密を知らない

署名鍵、DB credential、Bot Token、Stripe secret、Tunnel credential等はブラウザーへ出さない。

⑤ A案では同一origin BFFを維持

これによって現在の認証境界を大きく壊さない。

⑥ PC APIを将来B案の境界として設計

現在は内部APIだが、将来的にBrowser-facing APIへ昇格できるようにする。

⑦ PostgreSQLが永続状態の正本

Redisやブラウザー状態を正本にしない。

⑧ Rule Engineは提案者であって実行者ではない

AIは、

Detect → Explain → Recommend

まで。

は既存の明示的なNEXUS操作フローだけが担当する。

⑨ Suggestionは自動変更ではない

を維持する。

⑩ 外部結果不明は成功に変換しない

再送による二重操作を避ける。

⑪ PC停止とTunnel停止をRuntime状態と混同しない

Webが見えないことと、Automationが停止したことは別。

⑫ 0・No Data・Stale・Unknown・Unavailableを分離

現在状態を取得できないときに、偽の「0件」を表示しない。

⑬ PrivacyはRule Engineにも継承

AIを理由に取得データ・保持期間・guild横断識別を拡張しない。

結論

今回のコード監査によって、以前の「Web → Tunnel → Windows PC」という方針は成立することがかなり明確になりました。

ただし、正確には、

公式Web → お名前.com静的配信
Dashboard → Windows PC上のNext.js/BFF
Browser → Cloudflare Tunnel → Windows PC
BFF → 署名付き内部PC API
Analysis / Explore / Operations / Automation / Scheduler / Billing / Rule Engine → Windows PC
PostgreSQL → PC側の永続状態正本
Discord Gateway → PCから直接Outbound
Operator → PC localhostのみ

という構成がalpha16の基準になります。

そして、B案を将来可能にするために、PC APIをNEXUSの正式なDomain API境界として設計する。

この方針なら、alpha16で大規模な認証・Dashboard再構築を行わず、現在の実装構造を活かしながらRuntimeをWindows PCへ集約できます。

なお、料金についてはalpha16の設計契約へ数値を入れていません。Cloudflareの現行公式資料でTunnelの接続・origin設定は確認しましたが、料金プランを本設計の前提にする必要はないため、現時点では未確定のままとします。
