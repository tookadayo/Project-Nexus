3. A案で「直ちに必要な変更」と「将来B案のための整理」を分離する
3.1 alpha16で直ちに必要

Next.js Dashboard/BFFをWindows PC上で動かせる配置契約

app.example.com → Cloudflare Tunnel → Next.js

BrowserからPC APIへ直接アクセスしない

Session cookie、CSRF、guild認可の明文化

BFF→PC APIの内部署名

PC上のRule Engine

Suggestion永続化

Automation/Schedulerのクラッシュ安全性

Announcement/Statusの静的公開同期

PC/Tunnel/Runtime停止時の状態表現

3.2 alpha16では全面実施しない

現在のExploreやOperations等のNext.js→DB直接参照を、Tunnel対応だけを理由に全てPC API bridgeへ書き換える必要はない。

A案ではNext.js自体がPC上に存在するため、

Browser
  ↓ Tunnel
Next.js BFF
  ↓
PostgreSQL

はPC内部処理であり、A案の通信境界に反しない。

したがって、Exploreのgraph/viewsegmentやOperationsの各DB参照は、当面そのままPC内のserver-side処理として成立させる。

ただし、状態変更については、

BFF
 ↓
Domain Service
 ↓
DB / Outbox / Runtime

という責務境界を明確にする。

3.3 将来B案を容易にする整理

将来、Dashboardを静的化してBrowser→PC APIへ移行する可能性を残すため、

Browser DTOとDB schemaを直接結合しない

domain serviceをBFF routeから分離

PC APIのrequest/response契約を安定化

認証・guild認可処理を共通サービス化

DBアクセスをrepository/service層へ段階的に整理

client bundleへDB/API secretを出さない

Browser向けCORSを現時点では有効化しない

という整理を行う。

これはB案への移行準備であり、alpha16で静的Dashboardへ移行することではない。

NEXUS_API_URLはserver-side設定として扱い、Browser bundleへ公開しない。

4.2 Session cookie

推奨初期仕様：

host-only

Secure

HttpOnly

Path=/

SameSite=Lax

可能なら__Host- prefix

Domain属性を省略するとhost-only cookieとなり、__Host- prefixはSecure、Path=/、Domainなしという制約を持つ。

例として概念的には、

app.example.com
└── __Host-NEXUS_SESSION

とし、

www.example.com
other.example.com

にはsession cookieを送らない。

4.3 SameSiteだけをCSRF対策にしない

SameSite=Laxは初期方針として適切だが、それだけでCSRF防御を完結させない。

理由は、SameSiteがsite単位であり、同一registrable domain内の別subdomainとの関係を完全なorigin境界として扱うものではないためである。

したがって状態変更では、

CSRF token

Origin検証

state-changing GET禁止

POST/PATCH/DELETE等への限定

session認証

guild認可

を併用する。

CSRF tokenはsession単位でランダム生成し、URLやログへ露出させない。

10. Rule-based AI
10.1 基本方針

alpha16の「AI」は機械学習モデルではなく、

versioned deterministic Rule Engine

とする。

したがって、

同じFact
+ 同じevaluationAsOf
+ 同じruleVersion
+ 同じengineVersion
+ 同じthresholdConfigVersion

なら同じ結果を返す。

評価中に現在時刻を直接参照して結果を変えない。

11. Rule Definition

各Ruleは最低限以下を持つ。

ruleId
ruleVersion
engineVersion
thresholdConfigVersion

targetTypes
requiredFacts
evaluationWindow
minimumSamplePolicy
freshnessPolicy
missingPolicy
coveragePolicy

condition
explanationTemplate
recommendedActions
suppressionConditions

閾値はコードに埋め込まず、versioned configurationとして管理する。

閾値変更は同じRuleの結果を過去と混ぜない。

12. Data Quality

Rule Engineの出力には、数値とは別に品質状態を持たせる。

GOOD
PARTIAL
STALE
MISSING
SUPPRESSED

例：

activation_rate = 42%
data_quality = PARTIAL

の場合、

「Activationが42%だから改善が必要」

とはしない。

代わりに、

「Activationデータが部分的なため、コミュニティ改善提案の生成を抑止」

とする。

ただしData Health Ruleは、このような状態自体を改善対象として扱える。

13. Privacy suppression

初期候補として、以下を提案する。

用途	初期候補
Guild全体の一般aggregate	minN = 10
Channel/segment等の細分化	minN = 20
複数期間比較	各期間が最低母数を満たすことを要求
公開統計を将来扱う場合	minN = 30を候補
個人単位のAI提案	原則禁止

これらは未承認の初期提案値であり、確定値ではない。

また、単純なminNだけでは差分から小集団を推測できる場合があるため、

current count
previous count
subgroup count
overlapping subgroup

の組み合わせによる差分推測も抑止する。

18. 重複排除

同一の論理的提案について、

guild
+ target
+ targetVersion
+ ruleId
+ ruleVersion
+ thresholdConfigVersion
+ evaluationWindow

を基礎としたdedupe keyを使用する。

Fact snapshotが更新されるたびに同じSuggestionを大量生成するのではなく、

Suggestion
  ├── initial evaluation
  ├── subsequent observation
  ├── evidence update
  └── state transition

として履歴を保持する。

Rule versionが変わった場合は、旧Suggestionを勝手に新Ruleへ置換しない。

21. Suggestionの失効

以下の場合はSuggestionをactionableな状態から外す。

期限
now > expiresAt

→ EXPIRED

対象version変更
suggestion.targetVersion
    !=
current.targetVersion

→ INVALIDATED

Fact削除

Suggestionの根拠Factが削除された場合、

→ INVALIDATED

Guild削除

→ INVALIDATED

Rule変更

旧Ruleで生成されたSuggestionは新Ruleへ自動移行せず、

→ SUPERSEDED

として新RuleのSuggestionと分離する。

B. DNS方式

D. RESULT_UNKNOWNの再処理

推奨： 外部結果が不明な操作は自動再送せず、RESULT_UNKNOWNとして保持し、idempotencyまたは人間による確認がない限り副作用を再実行しない。

結論

今回の改訂で、alpha16は単なる「Automation＋AI」の追加ではなく、

「お名前.com＝静的公開層 / Windows PC＝NEXUS動的処理基盤 / Cloudflare Tunnel＝appへの通信経路 / Next.js BFF＝利用者認証・guild認可境界 / PostgreSQL＝永続状態の正本 / Rule Engine＝PC上の決定論的改善分析 / Suggestion＝人間が確認する改善提案層」

という、NEXUS全体の一貫したアーキテクチャになった。

特に重要なのは、A案では現在のNext.js BFFとserver-side DB参照を維持できるため、Tunnel対応のためだけにExplore・Operations等を全面的にAPI bridge化する必要はないことである。

同時に、Rule Engine、Suggestion、Automation Runtimeについては、将来のB案や大規模化を妨げないよう、Fact → Rule → Suggestion → Draft → Apply、Intent → Queue → Worker → External Resultという明確な責務境界を持たせる。

これをalpha16の全機能設計上の基準線とする。
