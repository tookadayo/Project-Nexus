# alpha16 Web authoring integration

Source implementation and fixture preparation, 2026-10-16. No test, typecheck, lint, build, browser, DB or migration execution has been performed. Formal source files and `next-env.d.ts` remain protected. These records establish source connections, not G4 acceptance or operational activation.

## Shared Web boundary and navigation

`apps/web/app/auth/public-boundary.ts` remains default-deny. Browser pages use GET/HEAD only. New BFF namespaces are registered by exact path/method and UUID segments; this does not expose the internal API, Operator, arbitrary callbacks or every `/api` path. Existing canonical Host, session, CSRF proxy, Origin, displayed-guild assertion and live server authority remain mandatory. Both `OperationsNavigation` and the dashboard sidebar link to existing independent workspaces, including Detailed Analysis, templates/preferences, health, maintenance, managed roles, experiments/interventions and the authoring workspaces below. Rule suggestion READ remains independent from external Apply/publisher activation gates.

## Issue mapping and explicit inventory census

`GET/HEAD /rules/issues` → `rules/issues/page.tsx` and typed Japanese/English editor. Exact `GET/HEAD/POST /api/rule-issues` → `RuleIssueRegistry` with request-local `MaintenanceAuthorizationProof`. GET returns scoped READ data plus current NEXUS permissions. POST accepts only UPSERT/DELETE using the domain's shared strict schemas, rejects scope/actor/source-value/approval fields, binds If-Match exactly to expectedVersion and forwards native CAS/CONFIGURE/feature checks. POST uses the session-bound CSRF header and same-origin gate; response caching is disabled.

The editor selects retained successful base-rule target candidates and native experiment/playbook metadata; there is no free-form Fact, target SQL, body text or personal input. Empty mapping/inventory is distinct from an explicit complete-census declaration. Both displayed inventory hashes are mandatory on save and the domain compares them with the current native inventory; additions or version/state changes return `ISSUE_REGISTRY_INVENTORY_CHANGED` rather than binding an unseen inventory. Validity is explicitly entered as 1–172800 seconds. Reading or saving this config does not establish causality, activate an experiment/playbook, collect new observations or enable external Apply.

The UI supports scoped list/new/edit/delete, current permission denial, empty/unavailable candidates, expiry aging, version conflicts, inventory changes, network failure, read cancellation, unsaved-edit cancellation/back navigation and in-flight double-click suppression. A write with uncertain outcome is never automatically reissued. Refresh requires review of unsaved input and clears stale form/version state before another edit. All state is component memory; no additional retained purpose is introduced by the Web editor.

## Native source configuration

`GET/HEAD /rules/sources` → typed Japanese/English editor. Existing Rule BFF narrow routes are `GET/HEAD /api/rules/source-config`, `/options`, `/:sourceId`; `POST /api/rules/source-config/revisions` and `/:sourceId/disable`. The writer sends the immutable revision UUID as Idempotency-Key and the exact baseVersion as quoted If-Match. The schema/service/BFF are owned by the source projection implementation; this Web integration constructs only its accepted definition fields.

Five definition kinds have ordinary-language selectors for saved flow/activation revisions, current intake-panel versions, currently eligible channels and saved events. Activity kinds are fixed existing structured signals. Durations use integer numeric controls with no executable placeholder/default, campaign class is a non-personal identifier, IANA timezone is validated, settings revision is shown and a mismatch requires explicit selection of the current revision. Seven-/28-day windows and event confirmation/attendance semantics are fixed by the canonical schema. Event start, creation and expiry timestamps are displayed from the existing source; the definition schema does not accept arbitrary new date boundaries. Missing candidates/settings/required numbers keep save unavailable. Persisted current-source validation remains server authoritative.

Channel participation binds `channelTargetVersion` to the selected channel's current saved capability-snapshot/metadata hash. A null/missing hash cannot be replaced by source-config version or another channel's proof, and keeps that selection/save unavailable. The list and options reads both use current READ and are handled independently: an unavailable options request cannot erase a successful saved-settings list. Unknown authoring permission or missing current list disables changes. Metric/source-health observations remain ANALYZE; settings do not expose those observation values.

READ viewing and CONFIGURE editing remain separate. `options.canConfigure` controls the editor; unknown permission cannot enable it. Operational approval remains false. Existing CONFIG retention policy, source provenance, health/coverage/eligibility and generation prerequisites are independently enforced; unapproved persistence returns `RETENTION_NOT_APPROVED`. A definition marked enabled is explicitly presented as configured enabled, not proof that native source evidence or operational generation is healthy. No raw metric values, personal identities, arbitrary code, SQL, approval claims or fabricated health/source values are accepted.

## Prepared evidence and limits

`GET/HEAD /rules/evaluations` connects manual evaluation and native health to the existing Rule BFF. All fourteen closed NativeSourceRequest kinds use the shared pure schema. Saved source heads provide exact source/revision/target seals; active Automation flow metadata, enabled report schedules and explicit issue-registry mappings provide their respective candidates. Independent candidate reads retain successful lists and label unavailable ones. UTC second/minute input controls reject invalid new values, preserve empty fields as unavailable and track intermediate invalid controls; period roles and three consecutive windows are explicit. Existing health UUID/revision references are entered only where the schema needs or permits them. Transient health is never automatically converted into retained reference/Fact input. Actual role permissions, cohort membership, observations, SQL, arbitrary code, approval and measured-profile values are never browser inputs.

The permission-requirement registry has no version selector in the existing options endpoint. Its editor therefore accepts only an existing native registry version and fixes targetId to the selected server; native current-registry comparison determines availability. This is an explicit UI limitation, not an invented requirement/permission proof. The advanced sealed input editor is limited to twenty UUID/revision references; the domain's canonical limit remains unchanged.

Native-health POST uses current ANALYZE and no persistence/communication key. Current READ job lookup remains independent. Evaluation chooses an unexpired active config and uses one exactly serialized body for request-key preparation and enqueue. Optional CASE01–CASE20 selection is unique/canonical. Independent `GET /api/rule-context` reads current READ catalog metadata: resource ID, case, version, typed target and observed/expiry times. Explicit `requestedContextIds` are unique, sorted UUIDs, at most twenty and one selected resource per Case. Missing/expired resources and a selected resource outside the Case filter stop the UI request without dropping or substituting it. Multiple resources for one Case require an explicit choice; a Case ID alone remains ambiguous at acceptance. Combined Case and resource selectors are an intersection. Case-only sends `inputs:[]`, a nonempty Case or context-resource selector and no nativeInputs; resource-only selection is valid. No raw context values or staff authorization are sent. Missing profile/context/base result remains a native acceptance failure. Job GET/status and native cancellation use current authority; cancellation re-reads the job, prepares its distinct EVALUATION_CANCEL key and retains the existing transaction-internal row_version CAS rather than inventing a client version field absent from the DTO. Acceptance, cancellation request and confirmed terminal state are distinct. No auto polling/retry or local retained purpose is added.

Unknown mutation results stop new evaluation/cancel submissions. Refreshing candidates does not clear that stop. A cancellation is reconciled only once the exact job state is no longer QUEUED/RUNNING. A lost enqueue response can be reconciled by an explicit `POST /api/rules/evaluation-request-status` using only the original prepared key retained in component memory. It is never displayed, persisted to browser storage, put in a URL or automatically resent. The current actor/scope/EVALUATE key hash selects the existing row; its stored fingerprint establishes the original HMAC binding. Missing rows provide no authority. Only exact valid HMAC plus matching original wire/DB expiry can yield PREPARED or DONE. PREPARED means acceptance remains UNKNOWN, including possible in-flight work. DONE resolves only its original EVALUATION reference to the same-actor, scoped, unexpired job within the same transaction and returns the existing safe metadata DTO. MISSING/EXPIRED/UNAVAILABLE keep submissions stopped for authorized-operator reconciliation. A DONE response explicitly restores the original job without re-enqueueing it.

The status method keeps current ANALYZE, live proof, tenant/deletion guards, canonical scope locks and a final clock/proof/receipt/job-expiry recheck. It neither invokes nested job/enqueue transactions nor introduces a new active-config, measured-profile or generation/WRITE retention gate for reading the already retained receipt. It performs no mutation, consumption, expiry renewal, new table/purpose, source collection or remote operation. The original native thirty-second ceiling and earlier source/config/key deadlines remain authoritative; this lookup does not change key issuance lifetimes. Japanese/English PREPARED/closed/DONE messages, permission/communication errors, explicit read cancellation, back/unsaved guards and in-flight suppression are source implemented. All verification remains NOT RUN.

Native health references follow the current shared schema: AUTO_RUN_OUTCOMES, REPORT_DELIVERY and STRUCTURED_ISSUE_PERIODS may omit references when their reader derives authoritative health. If supplied, original UUID/revision references remain strict. DATA_SOURCE_HEALTH still requires exactly one retained reference. No omitted reference is replaced by a transient observation or fabricated health value.
