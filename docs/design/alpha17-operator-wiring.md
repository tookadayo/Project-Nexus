# alpha17 Operator policy wiring

Base: `8d23caeacecd6b09672f5f8a5ef6901ad1e9271c`. This implementation does not approve an operating grant, retention duration, real credential, OS account, ACL change, database migration, network publication, publisher or restore provider.

## Local configuration contract

`scripts/operator.ts` exports `startOperator()` without starting anything on import. Production loads only the absolute `NEXUS_ENV_FILE`, `NEXUS_OPERATOR_POLICY_FILE` and `NEXUS_OPERATOR_CREDENTIALS` paths. The supervisor may explicitly pass its already-validated environment snapshot; Operator does not re-read that file, and an env-file production mode change during direct startup is rejected. The listener remains on `127.0.0.1` and a separate Operator port. A directly started production Operator also rejects a non-loopback database URL.

The non-secret policy is outside the checkout and outside the user-facing launch directory: proposed `%USERPROFILE%/NEXUS-RUNTIME/config/operator-policy.json`. `alpha17-operator-policy.example.json` deliberately has null approval dates and no grants, durations or maintenance schedule. It cannot be used as a valid policy until those exact values have been reviewed and approved. No command in this change generates credentials, creates this actual configuration file, repairs ACLs or starts a real server.

Schema version 1 requires:

- `revision` and approval `reference/approvedAt/validUntil`, with the current clock inside the finite approval window. References are bounded identifiers, not proof of a remote capability.
- `scope.guildIds/global`, explicitly chosen. Both permission groups share this exact scope to prevent a union of different read/write scopes from expanding a mutation grant.
- `readGrant.permissions`: only STATUS_READ, ADMISSION_READ, RECOVERY_READ, AUDIT_READ, CONFIG_READ, PUBLICATION_READ and LEGAL_READ (each with the OPERATOR_ prefix).
- `mutationGrant.permissions`: the remaining upstream Operator permission names. A read permission cannot be placed in this group, and a mutation permission cannot be placed in the read group. Both groups can be empty.
- `retention`: zero or more unique OPERATOR_PREVIEW, OPERATOR_STEP_UP, AUDIT and OPERATOR_CONTROL entries, each with an explicit finite positive `durationMs`, revision and approvalReference. Existing alpha16 caps remain enforced. Other data classes are not configured here.
- `stepUp`: null, or explicit positive previewMs/stepUpMs/challengeMs. Factor/challenge lifetime cannot exceed preview or its approved retention. No default periods are adopted.
- `maintenance`: null, or explicit batchSize (1–1000), intervalMs (1000–60000) and leaseMs (greater than one and at most two intervals, at most 120000). These values are operational choices requiring approval, not implicit activation.

Every file read checks an absolute OS-local path, no network/device path, no symlink ancestors, a regular non-symlink single-link file, a 64 KiB size cap, bounded read and stable file identity. Windows invokes the existing ACL verifier with `-Verify` only for the file and containing directory: private owner/SYSTEM/Administrators access with inheritance disabled. Other systems require current ownership and owner-only access. A failure is sanitized and fails closed; no path/content/PowerShell diagnostic is exposed.

The loader pins the entire initial file hash. Policy, grants and health metadata re-read the file on use, verify approval expiry, and reject any byte change until process restart. Grants never fall back to all permissions. An explicitly approved read-only file works with empty retention, null step-up and null maintenance; the dangerous command gates remain closed. A missing/invalid file cannot bootstrap an approved grant.

## Local TTL evidence

The existing privacy maintenance gate is unchanged. New `purgeOperatorEphemeral(batchSize)` processes only Operator previews, challenge/factor proofs, command replay rows, alpha16-tagged audit rows and controls. Each table has its own bounded batch; parent deletion waits until child batches are gone so an FK cascade cannot bypass the budget. Database statement and lock timeouts bound failure. An expired backlog returns not-ready. No deletion job, receipt, tombstone, backup or restore data is processed by this method.

The Operator server runs this pass on readiness and then serially at the explicitly configured interval. Only a successful no-backlog pass creates a short in-memory local enforcement lease. The deadline starts at pass start, not completion, and is the minimum of the approved lease, shortest original retention and policy approval expiry. Exceptions, an unsafe/changed policy, backlog, lease expiry and shutdown invalidate it. Shutdown clears the timer and waits for an in-flight bounded pass. A new process begins with no evidence.

The JSON cannot supply `enforcementVerified`, writer coverage, lifecycle/erasure scope, provider readiness, independent safety, restore readiness or publisher capability. Only these local Operator TTL classes receive code-derived enforcement during a current successful lease. Offline PC cleanup and independent backup expiry are not certified. Privacy deletion, global writer coverage, restore, publication safety and beta lifecycle scope remain under their separate existing gates.

## Preserved boundaries

Host/Origin/loopback/forwarded-header checks, local authentication, CSRF, alpha16 current permission/scope rechecks, preview hash/revision binding, fresh password step-up, idempotency and source-specific safety gates remain active. Existing legacy READ routes now require the same fresh explicit grant: guild list/detail use ADMISSION_READ and exact guild projection, audit uses AUDIT_READ and guild projection, overview uses STATUS_READ plus explicit global scope (unscoped counts are not fabricated), sessions use CONFIG_READ plus global, publication list/detail/preview use PUBLICATION_READ plus global, and legal settings/candidate preview use LEGAL_READ plus global. Empty or revoked grants cannot use an old route to read all guilds or private legal contacts. The two new read permissions are independent from ANNOUNCEMENT_PUBLISH/LEGAL_MANAGE and are never automatically granted. Authentication/bootstrap/logout and static assets keep their existing boundaries; historical mutations still require the reviewed command path (428). The policy does not imply a working Discord credential, public publisher, Tunnel, external Apply or CASE03/04 support.

## Verification

New synthetic unit tests cover strict schema, read/mutation separation, duplicate scopes, unsupported safety booleans, retention caps, bounded factor periods, current grant checks, local lease timing, approval expiry, file change/removal, oversized and hard-linked files, failed read-only ACL decisions, serial maintenance, retries and shutdown invalidation. Windows ACL calls are mocked in these tests; no actual host ACL is changed or claimed verified. Existing alpha16 Operator/retention unit tests remain relevant.

Final focused verification passed 58 unit tests in six files (including startup failure cleanup, import-without-startup, symlink rejection and validated environment snapshot use), plus four isolated Postgres integration tests verifying SQL batch limits, blocked FK cascade, fresh-row preservation, privacy-receipt/legacy-audit noninterference, legacy READ permission gates, exact guild projection, global-only aggregates, immediate grant revocation and an actual GLOBAL advisory-lock wait followed by local lease invalidation. The last case verifies unchanged guild revision/state, unconsumed preview/step-up proof and no command receipt. Confirm re-reads current policy after scope locks, after consuming proof, before transaction return (rolling all writes back on failure), and before external publication dispatch. The nine existing alpha16 Operator privacy integration tests passed after this change. The 14 existing official-publications integration tests also passed with explicit fixture-only read grants. The old UI renders a denied global overview as unavailable while preserving permitted guild reads, and never manufactures filtered global counts; its JavaScript syntax check passed. An initial three-file integration run had one existing PublicSessions parallel-refresh connection-pool timeout. The unchanged alpha12-sessions fixture repeated alone and reproduced the same approximately 600 ms connection-pool timeout in that first case; its other three tests passed. The existing 500 ms connection timeout and authentication/session-expiry conditions were not weakened. A separate synthetic cold/warm connection diagnosis is pending; real authentication and production readiness remain unverified. This is local fixture evidence, not real authentication, database operation, production readiness or remote publication evidence.
