## 2. これで解消したゲート

- 現行 CT01 が木か参照グラフか：木構造と判明。
- 共通 unknown の参照フィールドが既にあるか：`unknownRef` はないと判明。
- block ID の共有が可能か：重複禁止と判明。
- 選択枝終了後の通常動作：親へ暗黙合流し、空 unknown も合流すると判明。

このため、直前の第2回送信済み依頼と古い資料にある「実際の CT01 schema は未照合」は、本補足の範囲で更新する。保存互換・再開等価性まで証明済み、という意味ではない。

## 3. 未証明のまま残る変換等価性

共通 unknown 本体 U を各 CT01 の unknown に新しい block ID で複製すれば、報告された構造の範囲ではスコープ・終了範囲の制御を相当にできる。ただし、AST、意味 hash、実行識別子、制限消費は同一ではない。任意の unknown 本体の自動複製・自作ブロック移動が完全等価だとは判定していない。

特に次を第2回レビューで仕様化・証明する必要がある。

1. 新規 elif 列の専用 UI を既存の false 入れ子に保存する場合、列の範囲と通常後続の位置を明示する。
2. `A.otherwise = [B, 後続X]` では B の unknown 枝が通常終了すると X も実行される。`A.otherwise = [B]` の列と同一視せず、既存木からの自動折畳みを無条件で行わない。
3. 既存の各 if が異なる unknown を持つ場合、共通 unknown へ統合しない。通常の入れ子編集を維持するか、意味変更として明示確認する。
4. ID の割当て、意味 hash、再開 PC、既存 Run の定義固定、乱数キー、条件評価回数と制限消費、ローカル scope、Wait、break/continue/return、停止範囲を対比する。制限消費を隠して同一と扱わない。
5. 共通 U を procedure に移す案は、引数・戻り値・return、呼出し frame、終了範囲等の差を持つため、任意の unknown の保存互換な移動とは断定しない。
6. 新規 elif の追加・並替 UI と、旧定義の読取り専用表示・編集・保存・既存 Run 再開の互換を分ける。安全な一部の木だけを折り畳む案も、判定条件と反例を提示する。

## 4. R01 と R02 を混同しない

R01 は新設する有界 while/until の limit・unknown・エラー・期限等が通常の成功後続へ暗黙に落ちない契約の補完である。R02 は既存 CT01 の unknown 枝と elif 保存・UI の互換性である。

既存 CT01 の unknown 枝の通常終了が親へ合流する事実を、今回の追加設計だけで全面変更しない。反対に、この既存挙動を理由に新ループの limit や unknown を成功終了へ流してよいとも扱わない。新ループの非成功出口、明示 handler の到達先、hard-stop の優先順位を別途定義する。

外部 operation UNKNOWN の自動再送禁止・停止契約は引き続き優先し、条件 unknown と区別した状態遷移・試験を要求する。
