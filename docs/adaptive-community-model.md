# Adaptive community model v2 — alpha.5

NEXUS separates what Discord exposes, what the administrator wants to observe, and what actually happened after collection began. The [capability audit](discord-capability-matrix.md) records the official API and product references checked on 2026-10-02. Support means the documented metadata described there, not access to content or complete server history.

## Discovery and administrator confirmation

Discovery reads Guild features/counts, channels and effective View Channel permissions, accessible active threads, native Onboarding, legacy Welcome Screen, AutoMod rule counts and scheduled-event metadata. Nine bounded REST reads run through the existing rate-limit handling. Names and descriptions are not persisted in the capability snapshot. Display labels are fetched separately and cached for five minutes; they never assign meaning.

Installation, Guild/channel/thread changes and event changes enqueue a coalesced refresh. Structure changes debounce against the previous snapshot for one minute. Successful checks schedule the next refresh in 30 minutes; failures use bounded exponential backoff. Workers claim bounded concurrent batches with priority, fencing and jitter, with REST outside the privacy transaction. A dashboard render reads the stored snapshot instead of enumerating Discord structures again. Settings offers manual queued discovery.

Each feature has AVAILABLE, ENABLED, OBSERVED, CONFIGURED, UNAVAILABLE, PERMISSION_MISSING or UNKNOWN state and an available-since timestamp. AVAILABLE does not prove enabled or used. A successful legacy Welcome Screen read cannot prove it is enabled. Server Guide configuration remains unknown; only documented Home Action flags establish observed activity. Channel census is KNOWN only when the current Discord response proves the full count. Visible-only/obfuscated responses are lower bounds; historic totals are not reused. Accessible active thread counts are separate from the unknown total of private/archived threads. A failed endpoint does not become an empty server.

The administrator can combine SOCIAL, LFG_PLAY, SUPPORT_QA, DEVELOPMENT_FEEDBACK, EVENTS, CREATOR_FAN, VOICE and CONTENT_SHOWCASE. Channel purposes and Forum tag meanings require explicit mapping; suggestions derive only from structure. Neither a channel named “support” nor a tag named “resolved” creates a support or resolution rule. Saving uses the existing live authorization, settings revision, audit and actor-bound controls.

## Eligibility and newcomer progress

The member flags COMPLETED_ONBOARDING, STARTED_ONBOARDING, IS_GUEST, STARTED_HOME_ACTIONS and COMPLETED_HOME_ACTIONS are recorded from delivered metadata. Screening, guest and member flags have independent proof clocks. Legacy default-false rows remain UNKNOWN. Flags have their own observation timestamp so an old member join date cannot overwrite a newer pending state. Rules Screening pending members remain outside engagement measurement; an observed pending-to-cleared transition starts a fresh engagement clock. Native Onboarding completion never gates engagement. Guests can have a null joined_at and are tracked separately without inventing ordinary membership episodes.

First meaningful activity and later participation follow the confirmed modes. Text-oriented purposes use posts/thread membership; Voice/LFG use observed voice activity; Events use registration/observed attendance; Creator/Showcase can use reactions and poll participation. These medium or weak activities do not automatically become a strong first connection. Strong responses remain direct other-human replies, purpose-qualified first post responses, or threshold-qualified ordinary Voice co-presence. Onboarding flags alone are context.

New member progress shows counts for the same completed observation group, with still-observing and insufficient-coverage groups separately identified. Screening, guests and staff are excluded. Repeated/later activity windows remain the administrator's existing settings. Existing published activation definitions, experiments and alpha.3 canonical daily metrics are preserved; discovery does not silently replace them.

## Surfaces and interactions

Packets normalize to zero or more strict version-2 envelopes. Each packet retains stable sequence/session identity and ordinal. The ordinal-zero dedupe key remains compatible with queued alpha.3 envelopes; other ordinals have distinct keys. Guild Create and Thread List Sync restore mappings. Thread membership packets emit every added/removed member instead of just one event. Thread `newly_created=true` establishes creation; a newly visible old thread establishes only visibility. REST-discovered threads never receive a fabricated first response.

Text, Announcement, Voice text, Stage text, public/private/announcement Thread, Forum post and Media post are distinct surfaces. Children inherit the configured parent analysis scope and purpose. First other-human post response is measured from observed creation, guarded against concurrent duplicate replies. Being in the same thread is not a direct reply. Archive/lock are metadata; only an administrator-mapped RESOLVED tag establishes the configured resolution state. Forum/Media text, titles and attachments are discarded.

Reaction state is scoped by member, message and HMAC emoji/type. Add, remove, remove-all and remove-emoji update the active state. Metrics count distinct humans/user-message participation rather than treating several emoji as several people. Bots and self reactions are excluded; optional message_author_id or retained message metadata identifies the recipient. Unknown authors remain unassigned, and those active edges are excluded from verified other-human participation because self-reaction cannot be ruled out. No message REST lookup or emoji meaning is used. Historical alpha.3 received-response observations remain available separately from current participation.

Poll state uses a guild/message-scoped HMAC answer key. A member with several active answers is one participant in that poll. Removing the final answer clears participation; re-adding does not create a second first-participation fact. Questions, answer labels and opinion classifications are not collected. Active reaction/poll cards describe current state last observed in the selected window, not all past voters.

## Voice, Stage, events and safety

Voice join/move/leave maintains one session per observed member and one aggregate clock per channel. The clock advances only with at least two ordinary humans. Qualification uses observed co-presence seconds and the explicit product setting, default five minutes. AFK, bots, guests, unknown channel types and Stage are excluded from ordinary connection qualification. Member departure closes the session. Each periodic tick processes at most 500 candidates, prioritizing accumulated duration. There is no participant-pair graph. Disconnect/reconnect/publication gaps invalidate duration continuity; no period is reconstructed across missing observations.

Stage suppress=true indicates audience, suppress=false indicates speaker state; neither proves actual listening or speech. Stage entry and scheduled-event subscription remain distinct from attendance. Attendance requires a delivered ACTIVE status, a matching known Voice/Stage channel type, and observed presence during that active window. REST-discovered ACTIVE events lack an observed start and cannot supply attendance. External-event attendance is always unknown.

AutoMod execution retains a scoped rule hash, action type, user/channel/time only. Blocked content, matched text, keywords and rule names are discarded. Incidents and AutoMod are safety context, never a member bad-score or an ordinary sent message. Comparisons overlapping an incident carry a caveat.

## Scale and presentation

LOW_VOLUME, STANDARD and HIGH_VOLUME combine member count with joins, eligible observations, event rate and attention workload. HIGH_VOLUME applies at 10,000 members, 1,000 joins/30d, 10,000 events/day or 100 attention items. LOW_VOLUME requires fewer than 20 eligible members, fewer than 20 joins/30d and fewer than 100 events/day; other cases are STANDARD. Low samples use counts without prominent percentage comparisons. High volume presents bounded response queues, aggregate metrics and correctly labeled median/p75/p90 response times. New member progress uses the completed observation group as its denominator. Other cards distinguish event count, unique human sample, denominator, window and partial coverage; unavailable or irrelevant metrics are omitted.

Attention keeps the configured delay: ordinary text uses newcomer direct replies, observed Support posts use first other-human responses, and LFG posts use other-human participation. Only an observed new post with a known ordinary owner enters the mapped post queue; an older membership does not exclude a new support request. A Thread membership change can clear LFG attention without creating a strong connection. Voice/Event do not automatically generate attendance alerts.

Web Home, New Members, Attention, Insights, Goals & Rules and Settings use the confirmed profile. Insights switches overall, mapped channel and behavior views. Discord Components V2 uses compact corresponding panels and actor-bound settings. Radio Group (21) and Checkbox Group (22) appear only within modal Labels (18); message components do not contain modal-only controls. Forum tag mapping is available in Web settings; the Discord modal edits multiple modes, one channel purpose and the Voice threshold. Native client support for these controls still requires live Discord acceptance.

## Privacy, compatibility and verification

Migration 026 is additive: existing settings/envelopes/data remain valid. New discovery, mapping, state and fact tables are guild scoped. Member deletion removes subject/recipient state and facts, clears thread owner hashes and scrubs related durable payloads. Voice clocks are conservatively invalidated when a participant is deleted. Guild deletion clears all new tables and queued discovery. Detailed retention also expires new facts/edges and archived mappings; the latest capability snapshot remains for routing, while old snapshot history expires. Active structure mappings are routing state, not a historical activity log. No content, audio, DM, Presence, usernames or poll meaning is collected. No pre-install activity is backfilled.

Automated tests cover documented packets, all removal forms, duplicates, permissions, explicit mappings, partial discovery, Screening/Guest, restart restoration, no fabricated first response, event distinctions, deletion and retention. Seven representative profiles exercise stored backend selection and six Web/Discord views in JA/EN. Screenshot tests render real React components and actual Discord payloads; Discord screenshots are layout approximations, not evidence from a live Discord client. Performance includes the existing 10k/50k fixtures plus heavy Forum/reaction/poll/Voice data and a 600-person Voice stress check.

Live acceptance must check a Community and non-Community server, missing View Channel, private thread membership, native Screening/Onboarding/Guide flags, Forum/Media tags, all reaction removals, multi-answer polls, Voice moves/AFK, Stage state, known-active events, actor-bound modal edits and privacy deletion. Hosted Beta additionally needs privileged GuildMembers approval where Discord requires it, hosted operations and the previously deferred OAuth refresh/rotation/durable-revocation work. Soundboard/sticker/invite attribution and other deferred features remain explicitly listed in the matrix.

## Community Operations model v2

Presentation (Discord/Web) consumes Operations (Attention/recommendations/actions), Measurement (metrics/journeys/evidence), Community Model (purpose/recipe/scope/scale/goals) and Observation (facts/coverage/epochs). UI components receive domain presentation objects instead of interpreting raw DB rows.

Capability, observed usage, administrator intent and inferred traffic/scale are separate provenance domains. Community Model v2 adds entry mode, staff capacity, interaction mode and goals while preserving alpha.4 multi-purpose mappings. Invite/Apply to Join/Discovery are administrator context. Measurement starts after approved Discord membership; application counts, rejection rates and pre-join conversion are unavailable.

The four-step Web recipe wizard reviews features, observed usage, purpose and concrete measurements. Advanced mappings are collapsed. Seven immutable preset definitions and per-guild revisions are documented in [recipe presets](community-recipe-presets.md). Old confirmed profiles are retained as LEGACY_PROFILE, never silently upgraded to new semantics.

Recipe-specific aggregate transitions replace a universal funnel: social response/later activity, LFG response/co-presence/repeat activity, support response/confirmed resolution, signup/known attendance and voice repeat activity. Transitions do not provide an individual behavior timeline.

Attention distinguishes text newcomers, support/forum, LFG, event issues and integration failures. Team queue counts and acknowledgement/resolution distributions explain backlog without ranking staff. Recommendations require [evidence readiness](measurement-evidence-contract.md), same definitions/windows, sufficient sample, acceptable required coverage and no collection/integration/safety blocker.
