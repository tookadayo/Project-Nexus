# alpha15 ordinary role mutations

`discord.addRole` and `discord.removeRole` use one fixed Discord member-role endpoint. The flow revision contains an explicit role ID allowlist; it is separate from NEXUS manager roles. Every individual role operation requires a formal approval bound to the run, revision, exact evaluated inputs, and current permission-policy digest. A changed digest stops dispatch and requires a newly reviewed run. An uncertain external result stops the run without automatic repetition.

The requester must still have NEXUS CONFIGURE access, and the approving person must still have GOVERN access. Both actual current members and the Bot must have native Manage Roles (an existing Administrator is recognized). Role and target-member hierarchy are checked below each person's highest role, with the guild owner's native exception; equal positions fail closed. Targets cannot be bots, the guild owner, or pending members. Managed/integration/subscription roles and configured NEXUS admin, manager, staff and helper roles are protected.

Ordinary capabilities are an explicit permission-bit allowlist in `packages/discord/src/automation-role-policy.ts`: viewing/posting, attachments/embeds/history/reactions, ordinary voice participation, application commands, threads, activities/sounds, voice messages and polls. Administrative, moderation, mass-mention, webhook, invitation, unknown/future permission bits are excluded. The same restriction applies to role overwrite permissions. Adding or removing a role is evaluated across all current channels; removing a deny can grant access. Any gained capability must remain ordinary and already belong to both people in that channel. Both must currently see every affected channel. Restoring channel visibility must not activate a target's previously inaccessible administrative capabilities.

Dispatch is serialized per guild and capped at five role operation starts per rolling minute using existing durable operation timestamps. Definite Discord 429 responses recheck current authorization and the approved policy before another request. Other ambiguous write failures are never retried.

## Complete-channel evidence

The live Gateway GUILD_CREATE payload supplies a process-local channel-ID census. Channel changes update its generation; role/member/guild changes fence a policy check in progress. A disconnect, unavailable/deleted guild, invalid payload, obfuscated channel or missing census blocks role mutations. Current HTTP channels must match the exact census, contain full valid permission-overwrite metadata, and remain in the same generation throughout preflight. No channel names, message content, or persistent census records are added.

Discord announced on 2026-08-12 that HTTP will omit hidden channels from 2026-11-16, while Gateway still carries their IDs with obfuscated metadata and the `CHANNEL_OBFUSCATED` flag. Therefore HTTP alone cannot prove a complete impact calculation. The implemented profile permits ordinary access-changing roles when all required channel metadata is verifiable; it never changes Bot permissions or requests Administrator to obtain that proof. [Official channel-obfuscation announcement](https://docs.discord.com/developers/change-log#channel-obfuscation-for-users-and-bots).

The current combined `scripts/dev.ts` process shares this ephemeral census between Gateway, API and worker. Separately deployed Gateway/API/worker processes have no shared census and fail closed for role approval/execution. Supporting that topology requires an explicitly designed transient coverage transport; this implementation does not silently add shared persistence. After a Gateway disconnect, a fresh complete guild payload is required. Other adopted actions remain available under their existing checks.

Discord documents native role hierarchy and overwrite evaluation separately; Administrator does not bypass Bot role hierarchy. [Permissions and hierarchy](https://docs.discord.com/developers/topics/permissions#permission-hierarchy), [member role endpoints](https://docs.discord.com/developers/resources/guild#add-guild-member-role).

## Evidence

`tests/unit/alpha15-role-policy.test.ts` verifies ordinary access grants, removal of denies, privilege activation, native authority/hierarchy/protected roles, policy changes and complete census checks. Existing `alpha15-discord-transport.test.ts` retains narrow endpoint validation and ambiguous-write behavior. `tests/integration/alpha15-role-adapter.test.ts` verifies immutable allowlists, actual requester/approver reauthorization, saved digest comparison, burst limits and unknown-result handling in isolated PostgreSQL with synthetic Discord responses. Real Discord writes and deployments are intentionally outside these checks.
