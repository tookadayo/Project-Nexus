# Conditions before public operation

Publishing source code, displaying a document, saving private settings and
successfully running local tests do not approve public service operation.
Keep the following conditions unresolved until specific evidence closes them.

| Condition | Required decision or evidence |
| --- | --- |
| Legal documents | Final reviewed Terms, Privacy and Beta text; required operator information, separate contacts, effective date, version and regional details. Unfinished candidates are not public documents or consent targets. |
| Manager agreement | A currently authorized contract manager's adulthood, agreement authority and acceptance of the applicable published revision. Existing invitation activation is not such an acceptance record. |
| Installation and collection start | A defined, server-enforced introduction-complete condition and a confirmed installation/consent sequence. Bot presence or a UI checklist alone does not prove completion. |
| Pre-admission processing | Distinguish received events, temporary processing and persistent activity collection. Existing persistence checks do not establish that no temporary normalization occurs. |
| Provider and processing policy | Review actual personal-event classification, reply relationships, journeys and intervention paths. Aggregated output or document agreement does not itself establish that underlying processing is permitted. |
| Retention and erasure | Confirm periods and deletion coverage for source data, derived records, logs and backups; verify retries and monitoring. UI removal or a state transition is not proof of physical erasure. |
| Storage and restoration | Verify deployment-specific access protection, encryption and backup controls. Demonstrate restoration with current deletion records and revoked restored sessions before reopening traffic. |
| Support and rights requests | Establish distinct contact purposes, safe intake, proportionate identity verification and processing responsibility. A receipt is not completion, and an intake screen grants no authority to disclose or delete data. |
| Minors and regional processing | Resolve notices, provider/country details, applicable transfer arrangements and incident handling. Manager adulthood does not establish the age of every member. |
| Operational acceptance | Resolve the real Windows operator credential-file acceptance gap, real provider/permission checks and existing deployment, recovery and capacity requirements. Local synthetic checks are insufficient. |

## Boundaries that remain in force

New work requires the existing valid invitation, grant and installation state.
Expiry or suspension must stop new work while preserving only authorized,
retained history and the separate disconnect/deletion pathways. The bounded
history grace period does not authorize retaining every dataset for that period.

Keep the local operator listener separate from public routes. Authentication,
Host/Origin checks, CSRF, session expiry and revocation remain required. Public
reads must not obtain private settings, drafts or candidate legal text through
fallback, caches, metadata, print views or errors.

The admission model does not yet establish every agreement/introduction
condition above. Address missing enforcement explicitly; do not substitute
wording, silently assume earlier consent, or loosen existing checks.

[operator operations guide](alpha12-operator-operations.md) and
[known historical failures](alpha14-existing-test-failures.md) when planning
verification. This file is an operational checklist, not a legal conclusion or
a record that the conditions have passed.
